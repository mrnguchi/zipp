# M6 mobile API integration and local operation

Updated 2026-11-14. Implementation is present; suites and device flows have not been executed. Read [M6 behavior](M6_DELIVERIES.md), [evidence](M6_VERIFICATION.md) and [ADR 0010](adr/0010-m6-completion-and-mobile-contracts.md). This guide is not a test or deployment instruction.

## Modes and ownership

`mobile/src/screens/DeliveryScreen.tsx` chooses the existing visual demo or the feature-owned API flow. API mode requires `EXPO_PUBLIC_DELIVERY_API_ENABLED=true`; the default is false. The existing demo is a separate local flow with sample money and movement. It does not establish server payment or delivery success. Do not use its local PIN/fare/activity events in API mode.

The API flow is under `mobile/src/features/deliveries/`: booking/details/location selection, server quote/photo transport, snapshot/foreground polling, courier custody actions, issues, receipt/rating, tracking sharing and the pasted-capability viewer. Public contracts parse remote state/IDs/coordinates/dates and keep XAF as decimal strings. Components reuse the established design and React Navigation stack; no new navigation framework was added.

`features/identity/` connects the existing signup/login/verification screens in API mode. It supports signup SMS, password login SMS or authenticator TOTP, challenge resend, account profile hydration and single-flight refresh. Access tokens are memory-only. Native refresh tokens use device-only SecureStore; web credentials are memory-only. Passwords and challenge secrets never go in navigation params, public env, AsyncStorage or logs. Auth writes are serialized and generation-checked so a delayed response cannot restore a signed-out/switched account. Lost refresh rotation responses clear local credentials and require sign-in. Full identity management screens, social auth and wallet-provider UI integration remain their own work; local profile/role selections never confer API roles.

## Local setup, when a developer chooses to run it

1. Work from the appropriate `backend/` or `mobile/` directory. The compose path from `backend/` is `../infra/compose/compose.yaml`.
2. Identify `zipp_dev`, migration role and loopback port before migrations. Both M6 migrations were applied to this workspace's local database on 2026-11-14; other machines need their own identified deployment. Do not reset/seed a database or run `services:test` as setup.
3. Configure ignored backend keys through the existing M2 setup. Explicit local API choices are `AUTH_ENABLED=true`, `PRICING_ENABLED=true`, `ROUTING_ADAPTER=fixture`, `DELIVERIES_ENABLED=true`, `DELIVERY_CODE_ADAPTER=local`, `DELIVERY_MEDIA_ENABLED=true`, `DELIVERY_MEDIA_ADAPTER=local` and a persistent private media root. Compose already mounts that root only on the API. Give the independent worker the delivery flag/code adapter selection; never give it API identity keys or media volume. No flags were enabled by this completion pass.
4. In ignored mobile env, configure `EXPO_PUBLIC_API_URL` including `/api/v1` and opt into API mode. Use only an origin reachable from the device: Android emulator can use `http://10.0.2.2:3000/api/v1`; a USB device can use an explicitly arranged development port-forward. A physical device's `localhost` is the device itself. Do not widen Compose's loopback defaults automatically. Release builds require HTTPS. No credentials belong in `EXPO_PUBLIC_*`.
5. Rebuild the local application image/binary as appropriate when deliberately running the feature. JavaScript/Hermes export is not installation of native modules or proof of device permissions. The added SDK 58 native modules are included in the SDK's supported Expo environment; custom native binaries must contain them and the SecureStore plugin configuration.

No live SMS, payment, road-routing or object-storage provider is enabled. Existing routing accepts only the documented development fixture endpoints (4.05,9.7 to 4.06,9.72); selecting a different map route must fail rather than silently pricing straight-line distance. API-mode development builds provide an explicit local-route prefill button for these exact endpoints; it still obtains the fare from the backend and is absent from release UI. An empty server wallet stays empty. Funding/payment simulation must be a separate explicit local choice through M3; the mobile demo wallet never funds a backend booking.

## Booking and recovery

Sending puts the verified booker phone at pickup; receiving puts it at destination. Contacts must differ and use E.164. Require a package description, JPEG/PNG photo <=3 MiB, declared grams within the selected 2/10/20 kg size maximum and explicit terms/contact consent. Mobile hashes the actual bounded bytes and uploads raw octet-stream bytes using the intent; no local file path or base64 JSON is sent to the backend.

Obtain an expiring server Standard/Express quote, show its amount/route/expiry, then confirm. The client retains one booking key, quote, photo and canonical body across uncertain outcomes. It neither retries mutations automatically nor creates a new identity after a timeout. A known rejected expired quote/insufficient-funds response clears the pending attempt, since scoped replay was checked first. An unknown outcome freezes editing and offers recovery of the original request and persisted active-delivery refresh. On app restart, active deliveries/history are fetched before enabling a new booking. Status and settlement always come from the server.

Foreground status/tracking polling uses one in-flight request cycle, normally every five seconds, with bounded backoff for errors/Retry-After. It stops while the screen is unfocused/backgrounded or delivery is terminal. A lost connection removes the displayed current position; the persisted delivery and held funds are not changed. User switching clears cached delivery state. Server versions prevent older snapshots replacing newer selected state. Recent history is bounded to 50 rows in this screen; the backend's cursor endpoint supports further history integration.

## Contact proofs, courier actions and support

The app never invents, displays or receives a raw contact code from an API. An authorized request returns acknowledgement metadata, while the fixed sender/recipient phone receives the corresponding PICKUP/HANDOVER/RETURN code. In local simulation a developer can explicitly use `npm run delivery:code -- <requestId>` in the API process/container; this helper was not run. Guest contacts can receive real codes once the SMS adapter exists without registering an app account.

A registered contact can paste a delivery ID and claim its matching unbound role using its verified phone. Approved DRIVER accounts can explicitly go online, share fresh foreground GPS, inspect bounded offers and accept/decline with retained action identities. Acceptance rechecks shared busy/role/phone/proximity invariants. Current assigned couriers can record fresh foreground GPS and perform pickup/collection/transit/arrival/handover or authorized-return actions. Six-digit proof input is masked and cleared after submission. An application-suspended custodian uses the custody-scoped location endpoints; it receives no new DRIVER eligibility. Foreground location permission is requested only for a selected assigned courier job. Updates are bounded, sequenced and stop in the background. There is no background-location acceptance claim or new background permission/service.

Before collection the booker sees the snapshotted cancellation fee. After collection the UI opens a persistent support/return issue; it cannot cancel, release funds or force a terminal state. Independent recent-MFA ADMIN review remains in the M6 operations API. Receipts read actual charged/refunded/net amounts, and ratings are sent to the server after delivery. No local wallet balance is mutated by these actions.

## Tracking credentials

The mobile client generates an independent UUID plus 32 bytes using asynchronous native CSPRNG, registers `{id,secret,ttlSeconds}`, and retains the secret only in memory. The server returns `{id,expiresAt,revokedAt}`, never a secret. Identical registration input can recover lost acknowledgement without renewing or reviving access; changed identity input conflicts. Mobile preserves the same registration while its outcome is uncertain. Metadata lists let the booker revoke credentials whose secret was lost.

An explicit native share action discloses the credential to the user-selected recipient. It is not a tracking URL; do not append it to a deep link, query, fragment, analytics event or activity history. The receiving viewer accepts a pasted private credential and transmits it only as an Authorization bearer header. It sees status and at most coarse courier position during custody. It cannot see contacts/photo/money or request codes/change state. Revoked/expired credentials fail; terminal deliveries expose no location.

## Checks and limits

Version-specific official evidence and package peers are in ADR 0010. The SDK 58 crypto/store/file modules are pinned without major upgrades; npm hoisted the already-used file-system version instead of duplicating it. Type/build/export checks are distinct from actual native behavior. Added mobile API tests and updated photo/weight draft cases are written, not run. Android/iOS permission, background/resume, secure storage failure, flaky-network recovery, small/large devices, font scaling, accessibility, web and complete courier/contact flows need execution on the user's testing command. Real SMS/storage/routing/payment and background/native/realtime acceptance remain M8/M7/pre-release work.
