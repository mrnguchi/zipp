# ADR 0006: M3 ledger, reservations and payment execution

Date: 2026-11-12. Status: backend implementation and local development migration present; runtime verification pending. See [M3 evidence](../M3_VERIFICATION.md).

## Decision and worked examples

Implement a cohesive `finance` feature with focused wallet, payment and request-idempotency application services, pure money/transition rules, a persistence port/adapter and public facade. This avoids circular wallet/payment dependencies while keeping transport, domain and persistence separate. Reuse existing PostgreSQL 18.6, Prisma 7.10.1, BullMQ 5.76.4, Redis and Node 24.18.0; install no package and add no service. Preserve M2 and mobile.

Signed immutable ledger postings sum to zero per transaction. A top-up of 10,000 XAF posts customer +10,000 / clearing -10,000. Holding 2,000 changes reserved funds only: available becomes 8,000. Release restores 10,000 available. Capture releases that reservation and posts customer -2,000 / driver +1,800 / platform +200 for a caller-supplied, validated server policy example of 10% commission (not the selected production commission). Refund reverses original destination postings proportionally, floor allocation with residual assigned to platform, up to the captured amount. If recipient funds are unavailable, reject the refund for review rather than create an unauthorized overdraft. Payout posts wallet -amount / clearing +amount only after confirmed payment; confirmed failure releases its reservation. Unknown outcomes keep the reservation.

User balances cannot be negative or below reservations. Amounts use exact bigint; request amount maximum 1,000,000,000 XAF and account magnitude maximum 9,000,000,000,000 XAF are initial configurable-by-code bounds requiring future product review. Commission uses integer basis points and floor division; the driver gets the residual. Every posting has a business identity; refunds reference their original capture. No public arbitrary-credit/capture/refund endpoints.

Lock user rows in sorted order, then account rows in sorted UUID order, then the relevant reservation/operation. Current session/status and recent MFA are checked under the initiating user's lock for financial mutations. Staff approval requires FINANCE/ADMIN, recent MFA, reason and a different requester. Internal trusted reservation/capture/refund commands pass the existing opaque transaction context so future bookings can commit with funds. Database posting triggers update balances; deferred constraints enforce balanced transactions. App cannot edit posted ledger history or directly assign balances.

Persist scoped key/fingerprint and operation in the same transaction. Retain request identities; terminal response expiry is 24h and returns a conflict with operation ID thereafter. Pending/review operations do not expire. No destructive cleanup. Payment operations have stable UUID provider references. A database outbox is a durable command source; the worker relays small versioned IDs to BullMQ and rescans due records so lost queues/leases recover. Database leases prevent ordinary overlapping work; durable effect identities and the mock's reference-derived outcome protect replays after lease expiry. Bounded retries transition to review, never failure by assumption.

Payment mock is explicitly disabled by default, allowed only with PAYMENTS_ENABLED=true and PAYMENT_ADAPTER=local in development/test, and rejected in production. Server configuration chooses success/failure/pending/ambiguous outcomes; clients cannot select one. Local deterministic simulation performs no external calls; real providers require separate M8 ADR/contracts. No live SMS/payment or hosting enabled.

## Documentation and compatibility evidence

Reviewed 2026-11-12: [PostgreSQL 18 row locks](https://www.postgresql.org/docs/18/explicit-locking.html), [constraint triggers](https://www.postgresql.org/docs/18/sql-createtrigger.html), [BullMQ v5 worker API](https://api.docs.bullmq.io/classes/v5.Worker.html), [job IDs](https://docs.bullmq.io/guide/jobs/job-ids). The current Prisma transaction web page redirects to Prisma 8 examples; those APIs must not be copied into Prisma 7. Use installed generated Prisma 7.10.1 TransactionClient/$transaction types and existing verified M2 transaction adapter, with parameterized SQL for row locks. Dependencies and lockfile remain unchanged. Build/static compatibility can be checked; real-service/race/provider recovery remains unverified until tests are authorized.

Follow [ADR 0005](0005-financial-retries-errors-and-naming.md) and [financial reliability](../FINANCIAL_RELIABILITY.md). The M3 guide/evidence must record actual migration/build results and open gates. No tests/scans/load/probes run without the user's command.

Reference-access limitation: the hosted BullMQ v5 API request timed out; the official worker/job-ID guides and installed BullMQ 5.76.4 TypeScript definitions were used for the selected queue APIs. The Prisma 7 archive lookup was unavailable; existing generated 7.10.1 types and M2's transaction contract were retained. No Prisma 8 example or API was adopted. Provider/runtime semantics still require authorized integration verification.
