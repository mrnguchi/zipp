# ADR 0008: M5 booking, exclusive assignment and ride recovery

Date: 2026-11-12. Continued 2026-11-13. Status: backend source and local development migration present; tests/native integration remain unrun/pending by user direction. See [M5 evidence](../M5_VERIFICATION.md).

Continuation 2026-11-13: cancellation-fee disputes may also request a full refund of that original partial capture. Retain the original reservation amount plus explicit capturedAmountXaf; partial capture releases unused held funds and refund limits use captured funds, not the larger hold. Participant REST tracking may show an explicitly stale last-known snapshot between 15-30s; older or ineligible-session coordinates are unavailable. Booking admission is shared Redis 5/min/account in addition to global quotas. Runtime and mobile acceptance remain pending.

## Decisions and invariants

Add `jobs` (shared mobility job identity/active driver assignment) and `rides` (booking, dispatch, lifecycle/history/receipt/rating/disputes) modules. Reuse Node 24.18, Nest 12.3.3, Prisma 7.10.1/PostgreSQL 18.6, BullMQ 5.76.4 and existing Zod/Redis. No new dependency or service. Feature flags stay off by default; development-only pricing/routing and wallet mock limitations still apply. Mobile remains untouched until authorized integration/verification.

Booking consumes an owned unexpired ride-class quote, snapshots its server amount, commission, cancellation terms and service area, creates a job/ride and reserves funds, records request identity/audit/events and schedules dispatch in one PostgreSQL transaction. One active ride per requesting customer is the initial product limit; delivery concurrency is decided separately in M6. No client price/distance/payment success is accepted. Insufficient funds rolls back quote consumption and booking together.

Active assignment has unique driver user ID and unique mobility job ID, with one shared table for future RIDE/DELIVERY jobs. First eligible acceptance to successfully commit wins, not client tap time. Accept locks current actor/customer user rows in sorted order, driver application, job and ride, then validates the unexpired outstanding offer, account/session/approval/documents/class/fresh location, service-area membership, current radius and free assignment. Only then create assignment and advance state. PostgreSQL uniqueness is the final guard; process-local/Redis locks are not correctness protection. Other stages follow users -> driver aggregate when needed -> job/ride -> pricing area or wallet lock conventions; known rolled-back deadlocks have existing bounded retries. No network calls occur in transactions.

Dispatch is bounded PostgreSQL-backed work relayed to existing BullMQ: initial radius 2km, then 5km and 10km, 30s waves and 120s total search deadline. At most 10 new offers/wave, no repeat offer to the same driver for that ride, nearest observations first with UUID tie-break. Candidate discovery is a bounded indexed coarse filter; acceptance repeats authoritative checks. Geometric radius/arrival checks are proximity only, never road fare or guaranteed ETA. Offers disclose pickup/class/quoted fare, not customer contact, destination or completion secret. Decline/expiry cannot cancel an accepted job. No supply releases the hold atomically. Stale scheduled work rereads the same persisted job/state; losing a queue does not lose work. Permanent worker failures move work to review and retain funds, never invent success.

Lifecycle SEARCHING -> ASSIGNED -> ARRIVED -> IN_PROGRESS -> COMPLETED; SEARCHING/ASSIGNED/ARRIVED can end CANCELLED or NO_DRIVER as applicable. Arrival/start require assigned active eligible driver and a fresh observed position within 500m of pickup. Completion requires assigned driver, fresh destination observation within 500m and a six-digit CSPRNG customer-only completion PIN; no start PIN. PIN is purpose-bound HMAC using existing identity digest key, expires after 30 minutes, at most five failed proofs per 15min with durable counters that commit before error; customer issuance/rotation capped at 1/min and 3/hour. Raw code returned only on explicit customer issuance, never persisted/logged/events/offers. Lost code response can request a bounded new code. No unattended timeout releases an accepted assignment.

Completion atomically captures the held quoted amount into driver/platform accounts at snapshot commission, terminal state/event/receipt and assignment release. Customer cancellation before assignment has no fee. After assignment but before start, apply the user-authorized development policy cancellation fee capped at quoted amount, with commission under the same snapshot; partial hold capture releases its unused remainder. Driver cancellation before start releases the customer hold with no customer fee. After start, use a persisted dispute and reasoned recent-MFA ADMIN resolution; no automatic stop/refund on a network outage. Admin release cancels an unresolved in-progress ride without charge; completed-ride full refund uses the original capture and can fail for insufficient recipient funds, leaving dispute open. No force-completion/payment-confirmation shortcut.

Financial request identities are scoped by actor/action/UUID with canonical fingerprints, retained operation link and 24h terminal response window; same input returns current ride, changed input conflicts. PIN fingerprints use HMAC, not plain hashes of low-entropy codes. Assignment and settlement have separate business identities even across keys. Event records are versioned immutable outbox/history committed with state; bounded participant REST events/snapshot recover missed updates. Authenticated participant tracking snapshots expose only the assigned driver's latest eligible position during active assignment and stale timestamps; no location to unrelated users or old offers. Full Socket.IO/native map/background integration remains a documented M7/mobile gate; M5's backend REST recovery is not a claim of a working native live map.

`jobs` has no dependency on identity/drivers/finance. Drivers uses its public facade for free/busy eligibility and to block offline/vehicle edits during an active assignment. Suspension can stop eligibility but cannot silently free the assignment; support resolution is required. Finance account-closure checks shared active jobs to avoid stranding a driver/customer. Workers import enabled ride composition and independently scan bounded due tasks; API never starts consumers. No audio/calling is added.
