# ADR 0009: M6 delivery custody, contact proofs and restricted tracking

Date: 2026-11-13. Status: accepted; backend source implemented 2026-11-13 (see [M6 guide](../M6_DELIVERIES.md) and [evidence](../M6_VERIFICATION.md)); runtime/native/security verification pending on command.

## Scope and product rules

Add a feature-owned deliveries module using existing Node 24.18, Nest 12.3.3, Prisma 7.10.1/PostgreSQL 18.6, BullMQ 5.76.4 and Zod. Reuse shared jobs/finance/driver/pricing public facades; no new package/service or mobile change. Feature/media/code adapters stay explicitly local and disabled by default; production enablement is rejected until provider/runtime acceptance.

Booker is payer in both SENDING and RECEIVING perspectives. SENDING requires the booker's current verified phone as sender; RECEIVING requires it as recipient. Preserve explicit names/E.164 phones for both contacts. Resolve verified registered contact IDs server-side, never accept IDs/roles from clients or reveal whether a number is registered. A later registered contact can explicitly claim an unbound contact role by matching its verified phone; a bound historical role cannot be taken over. Assigned courier receives purpose-limited contacts only during the active job; offers contain no contacts, destination, photo or secret. Require explicit acceptance of terms/contact sharing. Contact/package/route data is immutable after booking; correction requires a valid pre-collection cancellation/new booking.

Package has a bounded description, SMALL/MEDIUM/LARGE size, declared grams (maxima 2/10/20kg) and a required owned JPEG/PNG photo <=3 MiB. These are provisional product limits, not provider/legal weight or prohibited-goods approval. Private create-only photo intents validate digest/size/signature and expire; one photo binds one booking. Reuse the bounded binary transport as a shared HTTP primitive, not a cross-feature presentation import. Local private files have a dedicated API-only volume, UUID keys, attachment downloads and no public directory; malware scanning/shared object storage/retention remain pre-production gates. File operations never run inside DB transactions.

Standard/Express require DELIVERY_STANDARD/DELIVERY_EXPRESS quotes, using M4 user-authorized sample fares/fixture routing until updated. Quote consumption, server term snapshots, photo binding, shared DELIVERY job, wallet hold, request identity, event and dispatch task commit together. Initially cap active bookings at three/booker. Dispatch uses 2/5/10km waves, max10 offers/wave,30s offers,120s total and authoritative acceptance checks, excluding booker/sender/recipient as courier. Shared unique driver/job slots exclude rides and deliveries across instances. Search exhaustion or valid cancellation before custody releases/partially captures funds atomically. Worker/queue loss does not release an accepted assignment.

Lifecycle: SEARCHING -> ASSIGNED -> AT_PICKUP -> COLLECTED -> IN_TRANSIT -> AT_DESTINATION -> DELIVERED. Custody: WITH_SENDER -> WITH_COURIER -> WITH_RECIPIENT. Courier arrival needs fresh position within500m of pickup; collection additionally requires sender PICKUP code. Recipient HANDOVER code and fresh destination position complete delivery and capture original fare. Proof purposes are separate; code delivery goes only to the immutable corresponding contact phone. Guest contacts need no app account: the assigned courier can request delivery of a code, but receives only a generic acknowledgement, never the raw code. Local simulation is a private developer mailbox, not real SMS or proof of real phone possession. Actual SMS/provider verification is M8 work.

After collection, no ordinary cancel or automatic expiry can discard custody, free the driver or refund. Participants open a bounded issue (recipient unreachable/return request/dispute). Independent recent-MFA ADMIN may authorize RETURNING with a reason and settlement choice RELEASE_HOLD or CAPTURE_ORIGINAL. No extra return charge beyond the existing authorized hold is created. AT_RETURN requires fresh pickup proximity; sender RETURN code commits RETURNED/RETURNED_TO_SENDER, authorized settlement, job closure and assignment release together. No admin force-delivered/force-returned shortcut. Unknown/unreturned packages remain held for explicit custody recovery; disabled accounts need reviewed offline/support recovery before pilot. Charged terminal outcomes can be fully refunded through original capture, with recipient/platform fund checks and no duplicate reversal.

Application suspension removes dispatch eligibility but must not prevent a still-active assigned custodian from safely returning a package. Provide delivery-scoped authenticated custody location epoch/update/return operations after collection, independent of new-job DRIVER approval. Caller must be the current assigned courier of an open WITH_COURIER delivery. This does not restore general dispatch eligibility or bypass account/session suspension; it only records location for existing custody. Shared assignment remains held. Native/background behavior is unverified.

Codes are six-digit CSPRNG, purpose/delivery/request-bound HMAC,15min expiry, at most1 issuance/min and3/hour/purpose;5 failed proofs/15min persist before error. Issuance does not reset failure counters. Raw codes never enter DB/queue/log/HTTP responses. Commit the digest/issuance state, then deliver outside the transaction. Delivery failure conditionally invalidates that exact digest and returns safe503; retry can issue a bounded new code after recovery. No worker receives identity signing/encryption keys or codes. Local mailbox helper can print a development code only on an explicit developer command; it is not an endpoint.

Tracking capabilities use independent random256bit secrets, store purpose-bound HMAC only, expire in8h (requested TTL10min..24h), and can be revoked by booker. Max5 active/max20 issued per delivery; list IDs to revoke a lost response. Secret is returned once, supplied as Authorization bearer header, never URL query or log. Public capability view contains status, timestamps and at most coarse3-decimal courier position during custody; no contacts/photo/PIN/money/identity or mutation permission. Terminal view has no coordinates. Capability holders cannot request codes, finalize handover, change custody or access participant endpoints. Registered participant tracking is separately authorized and precise. Digest rotation invalidates existing capabilities/codes; pre-production key lifecycle must be reviewed.

Requests/actions use retained actor/action/UUID identities and canonical fingerprints; code fingerprints are HMAC, not low-entropy plain SHA. State/event versions, custody, assignment, settlement and proof consumption commit together. Participant history/events/snapshots/receipts/ratings support reconnect; no Socket.IO/native/push delivery guarantee is claimed. Locks follow sorted users -> driver aggregate when needed -> job/delivery -> proof/photo/area/wallet resources; state/contact/assignment changes during initial lock acquisition cause safe retry rather than acquiring new user locks out of order.

## Completion amendments (2026-11-13)

- Sender and recipient phones must differ. This application rule keeps sender-bound PICKUP/RETURN codes and recipient-bound HANDOVER codes on different phones. It is not a database constraint, because the migration file may already be applied and is not edited.
- The migration's readiness marker `m6` is now required by API readiness, so the migration must be applied before an M6 API boots.
- The unused `delivery.returning` event type was removed from the generated contract. Return authorization emits `delivery.return_authorized`.
