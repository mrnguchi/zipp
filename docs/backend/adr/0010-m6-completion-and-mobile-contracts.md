# ADR 0010: M6 completion, client-owned tracking credentials and mobile integration

Date: 2026-11-14. Status: implementation; execution gates pending on user command.

The latest workspace instruction forbids returning tracking secrets in HTTP responses. This supersedes ADR 0009's one-time server-issued token response. An authenticated booker now submits a client-generated UUID and 256-bit CSPRNG secret in a strict request body. Store only the purpose-bound HMAC of `id.secret` and the requested TTL; return ID/expiry metadata. Same ID/secret/TTL replays the existing metadata, including revoked/expired status, without creating or reactivating a capability. Changed input conflicts. The public read uses the existing bearer capability header. Never put a capability into a URL, log, analytics, notification or activity history. Mobile keeps the credential in memory and can export it through an explicit native share action; losing it requires revocation/new issuance. Native share is a deliberate user disclosure, not an API response. A tracking viewer accepts pasted credentials and sends them only in the authorization header.

Add a forward-only completion migration rather than editing an unconfirmed/applied M6 migration. It records TTL for new capabilities and prevents equal contact phones at the database boundary. Existing capabilities are revoked on upgrade because their original TTL intent is unknown. Keep the foundation marker `m6`. Inspect the target database and migration history before applying additive migrations; never reset/seed it or launch a test stack.

Connect the delivery entry to a feature-owned API screen behind explicit `EXPO_PUBLIC_DELIVERY_API_ENABLED=true`. Keep the existing visual demo separate and unchanged outside the stricter photo/weight form validation. Live delivery never uses simulated money, courier movement or PINs. Use authenticated REST snapshots, server quotes and receipt/settlement fields. Reuse the current React Navigation stack and components; do not add Expo Router or rewrite unrelated screens. Foreground polling is bounded and stops in the background; reconnection always reloads server state. Background courier GPS/native behavior remains an execution gate, not a UI simulation.

The current auth screens are mock-only. API mode therefore connects signup/login/SMS or TOTP challenge verification and keeps access tokens in memory, refresh tokens in native SecureStore, and no password/challenge secret in navigation params. Web persistence is memory-only. Refresh is single-flight; a lost rotation response requires signing in again, never blind retries. Mutations retain the same action/request identity across uncertain outcomes. Booking retries reuse the exact quote/photo/body/key; app restart first reloads active deliveries before allowing new work. No local wallet is credited/debited by a server snapshot.

SDK compatibility reviewed 2026-11-14: installed Expo 58.0.19, React Native 0.88.0, React 19.3.0, TypeScript 6.0.3 and Node 24.18.0. Reuse SDK 58 package lines: expo-crypto 58.0.8 (asynchronous native CSPRNG and byte SHA-256), expo-secure-store 58.0.3 (device-only credential storage), expo-file-system 58.0.11 (bounded local photo reads). Installed Expo's bundledNativeModules ranges accept these patch versions; review package peer manifests before installation. Do not upgrade existing majors or hide peer conflicts. Native binaries must include the new modules; compilation/export alone cannot establish device readiness.

Official references read before implementation: [SDK 58 Crypto](https://docs.expo.dev/versions/v58.0.0/sdk/crypto/), [SecureStore](https://docs.expo.dev/versions/v58.0.0/sdk/securestore/), [FileSystem](https://docs.expo.dev/versions/v58.0.0/sdk/filesystem/), [ImagePicker](https://docs.expo.dev/versions/v58.0.0/sdk/imagepicker/), [React Native 0.88 networking](https://reactnative.dev/docs/0.88/network). Use `getRandomBytesAsync`, not the synchronous API with a development Math.random fallback. Private uploads use raw bytes with SHA-256 and exact size, JPEG/PNG only, max 3 MiB; no base64 JSON or client storage paths sent to the backend.

Write real-service fixtures with complete booking aggregates: a bare RIDE/DELIVERY job violates deferred consistency. Add missing receiving/contact-claim/suspended-custody/photo/HTTP source coverage. Tests, deliberate probes, scans and load runs remain unexecuted until expressly commanded. Static/build/migration evidence is recorded separately in M6_VERIFICATION.md. No hosting, real SMS/payment, provider account or optional monitoring is enabled.
