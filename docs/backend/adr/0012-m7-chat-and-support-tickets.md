# ADR 0012: M7.2 durable participant chat and support tickets

Date: 2026-11-20. Status: implementation; runtime/security/race verification pending on command. M7 remains incomplete.

## Decision and compatibility evidence

Add a cohesive `communications` Nest feature with REST commands/history, Prisma persistence and pure policy rules. Reuse Nest 12.3.3, Prisma/client 7.10.1, PostgreSQL 18, Zod 4.6.7 and existing unit of work, identity, audit and shared Redis limiter. No dependency/install/upgrade, socket mutation, worker consumer, native SDK or new service. API-only `COMMUNICATIONS_ENABLED=false` default, requires enabled identity, rejects production until acceptance. Migration is source only until an identified database step. Enabled bootstrap checks a separate `communications=m7_2` marker; base readiness remains `m6` so disabled communications does not require its tables.

Reviewed official [Nest controllers](https://docs.nestjs.com/controllers), [PostgreSQL 18 row locking](https://www.postgresql.org/docs/18/explicit-locking.html) and [Prisma transactions](https://www.prisma.io/docs/orm/prisma-client/queries/transactions) on 2026-11-20. Current Prisma documentation now redirects to a newer API (`db.transaction`); do not copy it into this pinned Prisma 7 workspace. The installed 7.10.1 generated `Prisma.TransactionClient` and existing `DatabaseUnitOfWork` establish version-specific `$transaction`, `findMany`, composite uniqueness and parameterized `$queryRaw` contracts; compilation/generation check compatibility, not runtime. No major upgrade is implied.

## Authorization and locking

One JOB thread per mobility job, immutable job type and creator. Only current ride/delivery participants may open/read/send/read-ack; public tracking capabilities and staff roles alone confer no job-chat access. Owning feature facades authorize and lock the job inside the caller's transaction, without exposing repositories or GPS. A terminal job's existing thread is read-only; it cannot acquire a new chat. Existing participants can read history while their account/session remains active. Newly verified delivery participants may read the existing job history after joining; old couriers lose access on reassignment. There is no arbitrary membership API.

SUPPORT threads are tickets, owned by the opener independently of optional job context. Creating a job-linked ticket requires current job participation; staff replies/history/queue/status changes require current SUPPORT or ADMIN plus recent MFA on every request. FINANCE alone has no ticket permission. Owners can read/reply and resolve/reopen their own tickets. No role shortcut grants money, custody or ride override authority. No emergency response promise; no private staff notes/attachments in this slice.

Lock order: owning job's sorted identity locks -> job row -> communication thread; support uses sorted opener/staff identity locks -> thread. Never lock a thread then acquire identity/job locks. For create-ticket the actor row serializes open-ticket counting and request receipts. Thread row serializes sequence allocation, receipt replay and status changes across replicas. Every receipt lookup follows fresh authorization. Replays precede writable/version checks, so a committed send can be recovered after resolution/terminal transition; newly unauthorized actors still cannot replay. Conflicting key/input returns 409. Read cursors use a maximum update under the same lock and cannot exceed committed last sequence. No network calls inside transactions.

## Persistence and recovery

Five named tables: `communication_threads`, `communication_messages`, `communication_read_cursors`, `communication_commands`, `communication_events`. Reviewed SQL adds foreign keys, bounds, composite uniqueness and limited application privileges. Immutable messages have per-thread contiguous sequence, author ID, plain text body and timestamp. Maximum 2,000 messages/thread; body 2,000 UTF-16 units and 8,000 UTF-8 bytes with control characters excluded (newline/tab allowed). No markup rendering, files, edits, arbitrary URLs fetched, typing/presence or delivery/read-by-other claims.

Create-ticket, send and ticket-status require UUID `Idempotency-Key`, scoped actor + operation + key. Canonical validated input is HMAC fingerprinted through existing identity crypto. Receipts contain only thread/message IDs, sequence and resulting version; no copied message body/token. They have no automatic expiry/key reuse. Same payload/key recovers that result after response loss; fresh authorized GET supplies current state. Unique job thread is the natural identity for open-job. Each accepted mutation stores its event/outbox intent in the same transaction; events carry references/version/type and optional controlled resolution reason code, never body/contact/secret. No publisher or push delivery is claimed. A later notification relay must reauthorize recipients and add durable delivery bookkeeping before consuming these intents. Read acknowledgement is private cursor state, not an outbox event.

History uses bounded ascending sequence keysets (default after=0, limit=30, max=50). Ticket lists use immutable UUID keysets (limit<=30), explicit owner/staff scopes and no message snippets. Thread version increments on message/status writes; clients resync via REST after reconnect. Initial account quotas: sends 30/minute, reads 120/minute, ticket creates 5/day, thread opens 20/minute, read acknowledgements 60/minute and status changes 10/minute, in addition to global REST quotas. Maximum five open tickets/opener. Rate-limit dependency loss fails closed before transaction work. Auth revocation/terminal races must be exercised before acceptance.

No automatic data deletion is enabled. Proposed body/history retention is 90 days after job end/ticket resolution, subject to product/privacy/legal approval and a later bounded archival job; active/unresolved/legal-hold cases cannot be swept on a timer. Receipt identities and integrity references must survive any future content purge. Message text may contain personal data: return it only through scoped no-store REST; exclude bodies/subjects from logs, audit and event intents. Thread growth limits are not a complete retention policy. Read receipts describe the actor's acknowledged cursor, not proven human reading.

## Verification and remaining scope

Write policy, application, HTTP and real database race/rollback/replay/authorization tests without executing them. Compile source and test source, generate/validate Prisma offline, build contracts, lint, format and inspect boundaries/config/docs. Do not migrate/seed/reset, launch runtime/failure probes, enable flags, deploy or call providers. Mobile chat/ticket UI integration, push/devices, calls/media/native, staff operations beyond ticket scope and measured fanout remain subsequent work. M7.1 stream stays read-only and does not broadcast chat.
