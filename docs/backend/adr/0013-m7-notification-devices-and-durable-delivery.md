# ADR 0013: M7.3 device ownership and durable notifications

Date: 2026-11-20. Status: implementation; migration/runtime/security/race/native verification pending on explicit command. M7 remains in progress.

## Scope and compatibility

Add feature-owned `notifications` with account/session-bound devices, a minimal inbox, transactional notification outbox and bounded BullMQ execution in the existing worker. No package/image upgrade, new container, paid service, real push provider, mobile native SDK, or live flag. Four new tables/migration source bring defined application tables to 54; last identified applied local evidence is still M6/45. Optional marker `notifications=m7_3` supplements base `m6` and requires the earlier communications migration. Migration is not applied as part of source implementation.

Reuse Node 24.18.0, Nest 12.3.3, Prisma 7.10.1, BullMQ 5.76.4 and existing PostgreSQL 18/Redis. Reviewed [Node 24 crypto](https://nodejs.org/docs/latest-v24.x/api/crypto.html), [Node 24 filesystem](https://nodejs.org/docs/latest-v24.x/api/fs.html), [BullMQ job IDs](https://docs.bullmq.io/guide/jobs/job-ids), [worker API](https://api.docs.bullmq.io/classes/v5.Worker.html) and [PostgreSQL 18 locks](https://www.postgresql.org/docs/18/explicit-locking.html) on 2026-11-20. Current Node latest-v24 is a later patch and the BullMQ v5 URL redirects to v6-labelled docs: installed Node 24 TypeScript and BullMQ 5.76.4 source/types plus existing queue lifecycle are the selected-version evidence. Retain the Prisma 7 generated-client/transaction contract from ADR 0012; do not copy newer Prisma/BullMQ APIs. No install is necessary. Dedicated AES-256-GCM encryption and HMAC proof/token hashes use HKDF-separated keys derived from `NOTIFICATION_DATA_KEY`, never JWT signing/enrollment keys.

## Ownership and privacy

Version-specific Node references were also successfully read before implementation: [24.18.0 crypto](https://nodejs.org/download/release/v24.18.0/docs/api/crypto.html) and [24.18.0 filesystem](https://nodejs.org/download/release/v24.18.0/docs/api/fs.html). The later-patch latest-v24 links above were not the sole evidence. BullMQ's redirect caveat still applies; no v6 API was adopted.

Initial adapter/provider is `capture`/`LOCAL` only. Accept only dummy `local_...` endpoints; reject actual Expo/APNs/FCM tokens until their provider-specific proof, application/project scoping, invalid-token and receipt contracts are implemented. A client installation has UUID v4 + client-generated 32-byte base64url proof. Store only its HMAC, never return raw proof/token. Installation owner is immutable. Re-registration/rebind requires the same owner, proof, active session and expected generation; identical endpoint/session retries recover the current generation. Actual changes increment generation, preventing delayed requests from reverting rotated endpoints. Revocation is terminal for that ID and clears ciphertext; it increments generation below the ceiling and remains permitted at the ceiling because revocation alone invalidates eligibility. A new installation requires a new ID/proof/dummy endpoint. Global token-hash uniqueness prevents duplicate endpoint bindings; LOCAL tokens do not establish ownership of any real device/provider address.

Max five live installations/account, 30-day registration expiry, 10 registration/revoke requests/minute/account, bounded input and general shared REST quotas. API authenticates and reauthorizes under the user lock. Ownership/proof failures use generic not-found. No transfer, arbitrary target-user field, admin token retrieval, raw token list or secret echo. Device expiry/revocation has no job/custody/financial meaning. Rebinding after sign-in must refresh session binding; a revoked/expired old session cannot keep receiving captures.

Inbox and provider payload contain only own notification ID, `ACTIVITY`, static text and timestamp. No thread/job ID/type, author/contact, message/subject, money/PIN, deep link, capability or JWT. Clients use authoritative authorized history/active-job/ticket APIs to retrieve detail, including after permission loss. A generic activity notice is not a grant of job access. Inbox access is account/session-owned, bounded UUID keyset pagination and idempotent mark-read; read is a client acknowledgement, not proof of human reading. Profile `notificationsEnabled=false` suppresses dispatch, but the private inbox still records activity for an active owner. Missing profile fails closed for dispatch.

## Atomic source integration

`communications` depends on the public notifications facade, never the reverse. When notifications are explicitly enabled at source commit, a new message creates one notification intent per current authorized participant except the author (deduplicated max four), and a staff ticket status change notifies the ticket owner. Job participant IDs come from the owning ride/delivery facade under existing identity/job locks. Staff queue arrival/paging is not broadcast to all support accounts. Only fixed internal sources can enqueue; no public arbitrary-send endpoint. Source event + notification intent + message/receipt commit in one transaction. Same source event/recipient is unique. Disabled notification enqueue does nothing and no historical backfill is implied on enablement.

The outbox stores only source event/recipient/type. Materialization locks the recipient, rechecks active account, then locks outbox and atomically creates the unique inbox and at most five delivery records for current devices, marking the intent complete. An inactive target is suppressed without inbox. For an active owner, expired intent, disabled preference or no device leaves inbox without push work. Devices registered after materialization receive no historical push replay. Source intents expire for dispatch after 24h, independently of durable action keys/history. No automatic deletion/key reuse.

## Delivery, retry and fencing

Existing worker scans up to 20 incomplete intents and 20 due deliveries every two seconds; queue jobs contain strict `{schemaVersion:1,kind,id}` only. PostgreSQL is authority; queue loss/completed job removal is recovered by rescans and durable uniqueness. Worker concurrency two. Producer has a two-second command budget; no process-local correctness or Redis-only deduplication. Notification feature/dispatch flags are separate, off by default. Worker uses existing identity/account read facades without API signing/enrollment keys; only the dedicated notification key is shared for endpoint encryption. API never starts a notification worker.

For each delivery, read identity, lock owner -> device -> delivery, check account/session, profile preference, device generation/revocation/expiry and intent expiry. A 30-second token-fenced database lease counts an attempt. Perform provider/file I/O outside the transaction with an eight-second abort budget. Recheck authorization/lease immediately before dispatch. Finish only a matching live lease; an expired worker cannot overwrite a newer attempt or revive an old lease. A post-preflight revoke can race an in-flight external action; generic payload and bounded timeout limit exposure, not a claim of instantaneous cancellation.

Capture writes a private, idempotent UUID-named JSON record containing delivery/notification/device ID and generation only. `CAPTURED` means local capture, never provider/phone delivery. Existing identical capture recovers after a crash; mismatching capture is not success. No push token, proof, body or account PII in captures/logs/queue. Future adapters must use stable delivery identity, reconcile ambiguous results and provide actual provider receipts; network exactly-once delivery is not claimed.

Retries use persisted exponential backoff/jitter capped at five minutes; maximum eight claimed attempts, then `REVIEW_REQUIRED`. A crash on the final attempt also reaches review after lease expiry. Expired intent, invalid session/device generation, disabled preferences or inactive owner are `SUPPRESSED`. A confirmed invalid endpoint revokes only the claimed device generation, never a newer registration. Unknown provider/decryption/storage errors remain bounded retries/review, not invented success or invalid-device revocation. No public force-delivered/replay endpoint. No effect on finance workers, reservations, jobs, custody or calling answer claims.

## Gates and later work

Write tests for current ownership/proof/generation/session, encryption/AAD/privacy, replay, race/rollback, queue/delivery fencing, crash/backoff/review, preferences and invalid-device conditional revoke; do not execute. Compile/generate/build/lint/format/static config/docs only. No migrations, seeds, services, probes, scans, tests, captures, provider calls or native flows are run by this pass. Native push permission/token registration and notification navigation, real providers/receipts, retention/archive and production enablement remain pending. Calling/OS incoming-call delivery is separate M7 work; generic capture notifications cannot substitute for VoIP push or media.
