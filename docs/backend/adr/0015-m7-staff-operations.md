# ADR 0015: bounded staff cases and owner-controlled actions

Date: 2026-11-23. Status: implementation in progress; no tests/migrations/runtime acceptance run.

Implement a feature-owned `operations` module in the existing API, default off. Reuse identity MFA/current-role checks, owning public facades, PostgreSQL transactions and Redis quotas. No new package, service, admin website, automatic fraud scoring or provider action. Existing driver verification, payment review/reconciliation, ride dispute/refund and delivery-return workflows remain the only owning action paths; operations does not create a generic force-status or arbitrary ledger API.

Staff with recent MFA may open bounded manual review cases against accounts, driver applications, rides, deliveries or financial operations. SUPPORT/ADMIN can inspect nonfinancial subjects; FINANCE/ADMIN can inspect payment subjects. FINANCE alone cannot read support/job cases; SUPPORT cannot read finance cases. Cases are manually raised allegations, never confirmed fraud or automatic suspension. Private bounded description is stored in the case only, excluded from event/audit/log payloads. Minimal subject summaries exclude contact details, coordinates, documents, PINs, payment secrets and private chat.

Cases have versioned OPEN/IN_REVIEW/RESOLVED/DISMISSED transitions, append-only metadata events and immutable actor/action/key receipts. A replay rechecks current role/session/MFA first. Changed input conflicts; keys do not expire or become reusable. Updates require an exact expected version. Audit and case events commit atomically; no publisher is claimed. Case/history/list reads are bounded, rate-limited, reasoned/audited, private and no-store. Page reports describe their page scope and never claim full-ledger/provider reconciliation.

An ADMIN can suspend/reactivate a nonstaff ACTIVE/SUSPENDED account only through an IN_REVIEW account case with expected case/account state. Reject self-targets and all staff targets; staff-role provisioning stays outside this API. Under sorted actor/target user locks, reject suspension with any active job/custody or unresolved financial operation. Revoke sessions on suspension; reactivation does not revive sessions, driver approval, assignments or holds. Never release jobs, custody, funds or active call reservations here. Existing participant checks/reaper deny/expire calls. No deletion/password/MFA/role mutation endpoint. Events/receipts identify the reviewed action without copying credentials or account PII.

Add `operations_cases`, `operations_case_events`, `operations_commands` with restricted grants, version/event consistency guards and a separate `operations=m7_5` marker. Other M7 migrations remain unapplied. Read schema target identity before any later migration; none is executed here. Source table count becomes 61, not a claim about the current development database.

Reviewed 2026-11-23: [PostgreSQL 18 locks](https://www.postgresql.org/docs/18/explicit-locking.html), [constraint triggers](https://www.postgresql.org/docs/18/sql-createtrigger.html). Existing Nest 12.3.3/Zod 4.6.7/Prisma 7.10.1 generated types and established transaction/validation contracts reused unchanged. No dependency install/upgrade. Write authorization, race, replay, rollback, HTTP and role-separation test source; execute no tests until commanded. Build/static checks do not establish security/capacity acceptance.
