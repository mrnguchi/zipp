# ADR 0016: self-hosted WebRTC/TURN direction

Date: 2026-11-23. Status: self-hosted direction chosen by user; native/relay implementation and acceptance pending. This does not mark M7 complete or authorize M8.

The user selected self-hosted WebRTC/TURN instead of a managed calling provider. Keep call signaling, audio and OS wake paths separate. Reuse M7.4 authorization/answer claims/receipts; adapt its diagnostic finite negotiation policy before exposing usable media. No static TURN credentials in the mobile bundle, recordings, managed media purchase, hosting or live provider activation.

Use a hardened authenticated coturn relay after version/image/architecture review. Proposed privacy default is relay-only (`iceTransportPolicy: relay`) to avoid disclosing participant network addresses directly; product confirmation and bandwidth evidence remain open. TURN REST credentials must be short-lived, bound to a claimed session/device/call and issued only after fresh eligibility checks. Shared relay secrets remain server-side/private secret files. Never conflate credential expiry with terminating an existing allocation/peer stream. Implement client media teardown on end/revocation, reconnect deadlines and relay allocation lifetime controls before enablement. Add CONNECTED/media reports only with an explicit trust model; client reports are not billing proof or verified bidirectional audio.

Coturn needs authenticated allocations, finite user/total quotas, bounded bandwidth and allocation lifetime, denied loopback/link-local/private/multicast/reserved peer ranges including IPv6, restricted management access and a reviewed UDP/TCP/TLS/media-port firewall/NAT layout. A general Docker bridge is not a complete phone-to-relay network. Local relay testing must explicitly bind the chosen LAN interface; do not expose an unauthenticated relay or publish new ports automatically. Pin a reviewed image digest before adding an executable Compose profile. No image/service/port is added by this ADR. `infra/calling/turnserver.conf.example` is a review template, not a launched or production-qualified relay.

Native inspection: mobile declares Expo ~58.0.19, RN 0.88.0, React 19.3.0. Official upstream source examined on 2026-11-23 identifies react-native-webrtc 155.0.1 and CallKeep 4.6.1, but those moving-branch manifests are candidates, not a selected published compatibility matrix. Expo config-plugin source uses workspace `catalog:` peers, which do not establish published package peer compatibility. WebRTC requires a development/native build; Expo Go cannot provide it. No candidate is installed and no native compatibility claim is made. Resolve published manifest/version/plugin/native architecture support together, then Android/iOS compilation and device acceptance on command. Preserve the current app; do not generate destructive native projects or relax peer constraints.

The existing `mobile/app.json` has no Android application ID, iOS bundle ID or Firebase/APNs configuration. Those product-owned identifiers and account availability were requested without asking for secrets. Native Android incoming-call integration requires its current Telecom/foreground/background policy; iOS requires CallKit/PushKit/APNs entitlement and valid-call reporting. Ordinary activity push is not VoIP wake. Private keys/service accounts belong in the approved secret store, never chat, Git, logs, or EXPO_PUBLIC variables. The M7.3 LOCAL device proof is not a real push token registration.

Reviewed primary resources: [WebRTC handbook](https://react-native-webrtc.github.io/handbook/guides/basic-usage.html), [Expo native requirement](https://react-native-webrtc.github.io/handbook/guides/extra-steps/expo.html), [WebRTC source manifest](https://github.com/react-native-webrtc/react-native-webrtc/blob/master/package.json), [CallKeep source manifest](https://github.com/react-native-webrtc/react-native-callkeep/blob/master/package.json), [Expo WebRTC plugin source](https://github.com/expo/config-plugins/blob/main/packages/react-native-webrtc/package.json), [coturn options](https://github.com/coturn/coturn/wiki/turnserver), [coturn configuration](https://github.com/coturn/coturn/blob/master/examples/etc/turnserver.conf), [Apple VoIP reporting](https://developer.apple.com/documentation/pushkit/responding-to-voip-notifications-from-pushkit), [Android calling](https://developer.android.com/develop/connectivity/telecom/voip-app). Installation/build/device/network/teardown/media/load evidence is still required. No tests, probes, provider calls, microphone flows or relay startup were performed.
