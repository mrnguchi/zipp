# ADR 0018: foreground native voice foundation, Android first

Date: 2026-11-23. Status: Android native foundation implemented and ARM64 debug APK assembled/statically inspected; iOS native build, tests, physical-device audio and M7 acceptance pending. Actual build history and artifact identity are in [native guide](../M7_NATIVE_VOICE.md).

The user returned to M7 voice calling and requested finishing that item before incoming-call push. Use WebRTC for audio and the existing authorized REST signaling for setup; retain read-only M7 sockets. Do not route audio through Nest/Redis, install CallKeep/push providers, enable an unqualified backend media mode or claim background ringing. Work in foreground native foundation -> relay -> scoped credentials -> call/media lifecycle -> teardown/reconnect order. Step 1 does not complete the later slices.

Installed project baseline inspected: Expo 58.0.19, RN 0.88.0, React 19.3.0, Node 24.18.0, Expo config-plugins 58.0.10. Published registry manifests inspected 2026-11-23: react-native-webrtc 155.0.1 (MIT, RN >=0.60), expo-dev-client 58.0.21 (MIT, Expo *). Pin both npm versions and their lockfile. Expo's installed bundled list recommends ~58.0.15 and current SDK58 docs recommend ~58.0.21, whose patch range is compatible. Registry archive SHA512 integrity was checked before installation. No forced peers/major mobile upgrade. Native compilation remains the real compatibility gate.

The published @config-plugins/react-native-webrtc 15.0.2 has Expo >=56 peer support (unlike its shorter README matrix), but inspection shows it adds camera, overlay, Bluetooth and wake permissions beyond this foreground audio scope. Do not install it. Use a focused local config plugin through the installed expo/config-plugins API for microphone/audio/network permissions, iOS microphone purpose text and removal of the unused WebRTC screen-projection service from the merged Android manifest. Preserve existing photo-camera permissions and app configuration. No permission dialog or microphone capture occurs during build/import.

Upstream Android module uses dynamic org.jitsi:webrtc:155.+. Pin reviewed Maven artifact 155.0.1 via a narrow generated Gradle resolution rule; same-major pin stabilizes the intended version rather than concealing incompatibility. Native iOS JitsiWebRTC remains governed by its podspec until the iOS build slice, with selected-version pod lock evidence required there. Do not claim an iOS native build from a Windows JavaScript export.

Native build opt-in uses a local calling-foundation profile and a development Android application ID, separate from future store identity. No production app ID is invented; user preference was requested. Require explicit development environment for this profile; never enable usable calls merely because a native module compiled. Release/default feature flags stay off. Existing backend local_control capabilities remain audioAvailable:false. A lazy feature adapter can expose microphone/peer cleanup primitives for later orchestrated calls; no screen starts recording or connects media in this slice.

Android tooling inspection found an existing SDK (platform37/build-tools37/NDK27.1), Android Studio Java21 and Gradle caches; default PATH Java17 and missing ANDROID_HOME do not mean the SDK is absent. Reuse tools without accepting new SDK licenses, modifying global environment, starting an emulator/app, uploading to EAS or provisioning hosting. Generated android directory must be new/ignored; refuse destructive clean generation over existing custom native files. Gradle assemble only, no test/lint tasks. Build/source checks are allowed under the user's no-test policy; test source may be written but not executed.

Observed native build issue: installed CMake 3.22.1/Ninja rejected a generated safe-area C++ object path longer than Windows' 260-character limit. Keep the workspace/toolchain in place; no registry changes, SDK/tool upgrade, source relocation or vendor patch. Extend the local plugin to pass `-DCMAKE_OBJECT_PATH_MAX=240` through app defaultConfig externalNativeBuild.cmake.arguments, preserving other arguments and RN's CMake setup. [CMake 3.22 documentation](https://cmake.org/cmake/help/v3.22/variable/CMAKE_OBJECT_PATH_MAX.html) describes deterministic hashing for long full object paths (minimum configurable limit 128); [Android's native build configuration](https://developer.android.com/studio/projects/gradle-external-native-builds#configure-cmake) documents this argument channel. Installed RN 0.88 NdkConfiguratorUtils reads/appends the same argument collection. Regenerate reviewed config without cleaning and rerun assembly only; record the actual result separately. This addresses an observed build failure, not a native runtime acceptance gate.

Observed CLI behavior correction: installed Expo CLI 58.1.15 prebuild/index.js sets clean to `!args['--no-clean']`. Earlier refresh commands omitted that flag and recreated this pass's generated Android tree, losing build/task cache. The preparation helper now explicitly passes `--no-clean` as well as refusing an existing native directory. Any later deliberate refresh must preserve that explicit flag and review existing native changes. Do not infer preservation merely from omitting `--clean` or silently repeat a destructive refresh. See the native guide/logs for the actual build history.
